# flaky — Specification (v0.1)

`flaky` repeatedly runs a test command, reads JUnit XML from each run, and ranks
intermittent failures. It is a single offline Go binary. This document is the
v0.1 contract; `docs/PLAN.md` is its implementation plan.

## 1. Scope and invariants

- No project configuration, network calls, external Go dependencies, or writes
  by `flaky` inside the source repository. Commands run in disposable copies.
- A command's nonzero exit is a valid test run if it produced parseable JUnit.
  A missing, empty, or malformed report is an infrastructure error, never a
  passing run. All temporary paths are removed on success, error, and signal.
- Command launch errors are reported before looking for JUnit. Command stdout
  and stderr are drained continuously; only the last 8 KiB of combined output
  is retained for missing-report diagnostics, regardless of output volume.
- JUnit is the input boundary. Runner specific conveniences locate its output;
  no framework output is parsed directly.
- Only observed test cases are counted. A skipped case and an absent case are
  neither a pass nor a fail. Missing cases are reported as incomplete coverage.

## 2. CLI

```
flaky [-n N] [--parallel P] [--junit RELPATH] [--json] -- COMMAND [ARG...]
flaky bisect TEST-ID [--runs N] [--junit RELPATH] [--json] -- COMMAND [ARG...]
flaky --help | --version
```

Flags precede `--`; command arguments follow it unchanged. `-n` defaults to
20, `--parallel` to 1, and `--runs` to 30; all are positive integers. Bisect
requires at least 30 runs, caps at 1000, and is sequential per commit.
`--parallel` is scan only. `--junit` is a relative path within each disposable
workspace and must not escape it or pass through a symlink. If absent,
supported runner adapters set the path; cargo-nextest and custom commands
require it. `--json` sends one JSON object to stdout, with no progress messages.
Version prints `flaky <version>` and help prints usage. Invalid flags,
missing `--`, empty command, or an unsupported runner with no `--junit` exit 2.

Exit codes: 0 = completed scan or bisect (even if failures were observed);
1 = target test ID absent in bisect; 2 = usage, command launch, report, git,
or workspace error; 3 = statistical classification inconclusive at a sampled
commit. Errors are `flaky: MESSAGE` on stderr. Ctrl-C exits 130 after cleanup.

## 3. JUnit discovery and runners

Every command receives `FLAKY_JUNIT_XML`, an absolute unique report path, and
`FLAKY_RUN_INDEX`, the 1-based run number within its scan or commit sample.
The report is deleted before the run. Explicit `--junit RELPATH` points to a
file the command writes in its workspace and takes precedence. With no flag:

| Command basename | Behavior | Report read |
|---|---|---|
| `pytest` or `python -m pytest` | append `--junitxml=$FLAKY_JUNIT_XML` | env path |
| `gotestsum` | append `--junitfile=$FLAKY_JUNIT_XML` before its `--` | env path |
| `jest` / `npx jest` | set `JEST_JUNIT_OUTPUT_DIR` and `JEST_JUNIT_OUTPUT_NAME`; the project must already have `jest-junit` reporter installed/enabled | env path |
| `cargo nextest run` | no automatic adapter; configure `.config/nextest.toml` `[profile.default.junit] path = "junit.xml"` and pass `--junit target/nextest/default/junit.xml` | explicit path |
| other | require `--junit RELPATH`; command can use `FLAKY_JUNIT_XML` | explicit path |

For jest, env variables are understood by jest-junit; Jest itself has no
built-in JUnit reporter. For nextest, v0.1 does not edit the project config;
the JUnit path is relative to workspace root. `--junit` is required even if
the config exists, because nextest writes under `target/nextest/<profile>/`.
The user may always pass `--junit` for a custom setup. A report generated by
an unrecognized command is read only when `--junit` is given.

## 4. Data model and identity

Each JUnit `<testcase>` has `classname`, `name`, and optionally `file`.
Canonical ID is `classname::name` if classname is nonempty, otherwise
`file::name` if file is nonempty, otherwise `name`. Trim surrounding whitespace
from fields; empty name is an error. Suite names do not affect identity.
`<failure>` or `<error>` makes the case fail; `<skipped>` makes it skip;
otherwise it passes. Duplicate IDs in one report are an error. XML root may
be `<testsuite>` or `<testsuites>`; nested suites are accepted. An empty report
is an error. XML entity decoding follows `encoding/xml`.

Run: index (1-based), command exit status, cases, duration, and report path.
Case observation: ID, status (`pass`, `fail`, `skip`), `message`, and output.
For a failure, output is the first nonempty `<failure>` or `<error>` body,
falling back to its `message`, capped at 8 KiB; a pass uses `<system-out>` if
present, capped at 8 KiB. A summary stores passes, failures, skips, missing,
rate, and one representative failure and pass output (first occurrence in run
order). `missing = total runs - passes - failures - skips`.

The failure rate is `f / (p + f)` when `p + f > 0`; otherwise it is null in
JSON and `—` in text. A test is **flaky** iff `p > 0 && f > 0`. Ranking: flaky
first, descending failure rate among flaky tests, then fail-only tests,
pass-only tests, skipped-only tests; break ties by ID ascending. The table
includes all observed IDs, not just flaky ones. Since a 100% failure is not
intermittent, it appears after all flaky tests.

## 5. Scan behavior and output

Resolve the current directory once. Copy its files recursively to a fresh
temp directory per run, excluding `.git`; symlinks are copied as symlinks,
never followed. Run with cwd set to the copy. Run indexes are assigned before
parallel execution; aggregate in index order. `--parallel P` launches at most
`P` commands concurrently. A cancellation terminates active child processes,
waits for them, and removes all copies. The source tree is never the cwd of a
test command.

Text output (UTF-8, tabs expanded by Go `tabwriter`, no color):

```
FLAKY  20 runs · 2 tests · 1 flaky
RATE    FAIL/PASS  MISS  TEST
25.0%   5/15       0     pkg::test_a
100.0%  20/0       0     pkg::test_b

pkg::test_a
  fail: expected 1, got 2
  pass: expected 1, got 1
```

The detail block appears for each flaky test only. Embedded newlines in
output are indented by two spaces; empty pass output prints `(no output)`.
The table header and every row are stable. Nonflaky rows have no detail.
Counts in `FAIL/PASS` are failures/passes. A missing test has `MISS > 0`.

JSON is a single object with keys in this order:
`version`, `command`, `runs`, `tests`, `flaky` for scans. `tests` is an array
in table order. Each entry has `id`, `passes`, `failures`, `skips`, `missing`,
`failure_rate` (number or null), `flaky`, `failure_output`, `pass_output`.
`flaky` is count of flaky tests. Paths are not exposed in JSON.

## 6. Bisect

Require a git repository and a clean tracked/untracked working tree before
bisect. Record `HEAD` and obtain `git rev-list --first-parent --reverse HEAD`.
The oldest commit is a presumed stable anchor; `HEAD` must be classified
flaky. Each run of a sampled commit gets a fresh checkout with `git worktree
add --detach` under a temp parent and is removed with `git worktree remove
--force` after that run, including on Ctrl-C. `flaky` never checks out or
resets the user's branch. The test command runs in that disposable worktree,
with Git metadata available. Git's own `.git` worktree metadata is temporary;
no project source file is changed.

For each commit, perform exactly N independent runs. Let `f` be failures and
`p` passes for the target ID; skips/missing do not count. Require `p + f = N`
or classify as inconclusive. Use a two-sided 90% Wilson interval for the
binomial failure probability with `z = 1.6448536269514722`:

```
q = f / N
d = 1 + z²/N
c = (q + z²/(2N)) / d
h = z * sqrt(q(1-q)/N + z²/(4N²)) / d
interval = [max(0,c-h), min(1,c+h)]
```

Classify **stable** if upper bound `< 0.10`; **flaky** if `p > 0`, `f > 0`,
and lower bound `> 0.10`; otherwise **inconclusive** (exit 3). A target absent
from every report at a sampled commit exits 1; partial absence is inconclusive.
At N=30,
0 failures is stable; a small nonzero failure count may be inconclusive.
The oldest anchor must be stable and HEAD flaky. Binary search the first-parent
list for the first flaky commit; if a midpoint is inconclusive, stop with exit
3 and print its hash and interval. If the first-parent history is not
monotonic, this reports the earliest boundary within the sampled path, not
all independent origins. Cache observations by hash so no commit is sampled
twice. `--runs` sets N at every commit; no adaptive stopping.

Bisect text output:

```
BISECT  pkg::test_a · 30 runs/commit · threshold 10% (Wilson 90%)
FIRST   abc1234  subject line
PARENT  def5678  stable (0/30, 0.0%–8.3%)
FIRST   abc1234  flaky (8/30, 14.2%–42.3%)
```

Full hashes are in JSON. JSON keys: `version`, `test_id`, `runs_per_commit`,
`threshold`, `confidence`, `first_commit`, `parent_commit`, `observations`.
Each observation has `commit`, `subject`, `passes`, `failures`, `lower`,
`upper`, `classification`; observations are in sampling order. A root first
commit has null `parent_commit`. Inconclusive reports print the same header
and `INCONCLUSIVE HASH (F/N, LOW%–HIGH%)` to stderr.

## 7. Files and release

`cmd/flaky/main.go` owns process entry and signal exit; `internal/flaky/`
owns CLI, JUnit parsing, workspace execution, statistics, rendering, and
bisect. `docs/SPEC.md`, `docs/PLAN.md`, `README.md`, `LICENSE`, `go.mod`,
`.goreleaser.yaml`, `.github/workflows/ci.yml`, `.github/workflows/release.yml`,
`ARCHITECTURE.md`, and `CONTRIBUTING.md` are tracked. No reports, cache, or
state are written to the source repo. `.git/info/exclude` locally ignores agent
files listed in the request. Go module path is
`github.com/dpologdvinity/flaky`, Go 1.23 minimum, MIT © 2026 Kaitlyn
Bassford. CI checks `gofmt -l .`, `go vet ./...`, and `go test ./...`.
Release artifacts are GoReleaser single binaries for Linux, macOS, Windows,
amd64/arm64 where supported. Pushing a `v*` tag publishes a GitHub release;
the release workflow updates `dpologdvinity/homebrew-tap` when its token secret
is configured.

From v0.1.2, the release build job generates GitHub build provenance attestations
for every `.tar.gz`, `.zip`, `.deb`, and `checksums.txt` asset using GitHub Actions
OIDC and `actions/attest`. Only that job receives `id-token: write` and
`attestations: write`; no signing-key secret is required. Before updating
Homebrew, it downloads the published assets and verifies their signatures against
this repository, release workflow, source tag, and commit, requiring GitHub-hosted
runners. It also requires rejection of a modified checksum file. Users can
verify downloads using `gh attestation verify` as documented in the README.
Older releases remain unchanged. The curl installer retains SHA-256 verification;
it does not require GitHub CLI or automatically verify attestations.

Linux releases also include `.deb` packages for amd64 and arm64, installing
`/usr/bin/flaky` and `/usr/share/doc/flaky/copyright`. The existing signed APT
repository at `https://dpologdvinity.github.io/packages/apt/` imports published
packages hourly without changing its signing key or repository identity.

`install.sh` installs the latest release on Linux/macOS amd64/arm64 after SHA-256
verification. Its default destination is `$HOME/.local/bin`, overridable with
`FLAKY_INSTALL_DIR`. Installation replaces the executable atomically only after
verification and cleans temporary files on exit. See `docs/INSTALLATION.md` for
the distribution design and acceptance checks.
